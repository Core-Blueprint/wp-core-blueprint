# DP-NAV-02C — Canonical Document Rendering Reliability Gate

Owner: **Core Blueprint Base**. Overseer #94. User-approved architecture
(2026-11-15): **Dompdf = canonical PDF generation and physical layout;
PDF.js = canonical browser display for every paginated Document Designer;
Base Designer = sole authority for Selection, Inspector, History, Save and DND.**

Reports, Contracts and future Document Flow consumers use the same public
Base Flow paged host. No consumer-specific PDF pagination or competing canvas
renderer. Mail is not paginated. No Node server, external PDF API or CDN.

## Dependency and deployment admission — mandatory before release

- Pin official npm `pdfjs-dist@6.5.438` and vendor with
  `python3 tools/vendor-pdfjs` on a network-capable developer checkout.
- `tools/vendor-pdfjs` invokes **official npm** without package install
  scripts, checks the tarball against registry SHA-512 SRI, extracts only
  display/worker/renderer modules, needed CMaps, fonts, WASM and LICENSE,
  and writes a SHA-256 file manifest. The vendor directory is exclusively
  generated by that script; do not hand-edit third-party assets.
- Review `assets/vendor/pdfjs/manifest.json`, LICENSE and security
  advisories. Confirm Apache-2.0 plus GPL-2.0-or-later compatibility and
  comply with required redistribution notices.
- Commit the audited vendor artifacts on the featurebranch. Both canonical
  `tools/build-release` and dev packaging reject absent or changed vendor
  bytes. Developer workstation Node/npm are **build-time only**; the installed
  WordPress plugin runs on existing PHP + MariaDB hosting.
- Verify `.mjs` JavaScript MIME on the actual LiteSpeed/Plesk site and
  the same-origin module-worker policy in CSP; neither a runtime CDN nor
  silent fake worker is acceptable.
- Source identity: only the **same** Dompdf request produces the PDF
  snapshot and its page-local semantic region mapping. The endpoint is
  read-only POST, current nonce, capability, authenticated user, strict
  typed {project,fields}, bounded body/output, no-store responses and
  no site writes. A lost response is not a document Save.
- Main remains untouched until Chris explicitly approves merge.

## Document Rendering Reliability Gate — mandatory FIELD proof

1. Real installed Reports Designer shows **separate A4 sheets**, no inner
   iframe scrollbar, and accurate page count plus navigation.
2. Single, explicit 2-page, 4+-page split paragraph, nested region and
   table spill fixtures match exported Dompdf PDF. Confirm first/last line
   positions, page counter and repeated header/footer behavior. Dompdf
   cannot split a single table **cell** across pages; reject/handle such
   authoring before claiming parity.
3. Selection of a block on each page maps to the correct semantic node
   and the existing Layers/Inspector; nested elements win over parents.
   One visible selected outline from Base, no duplicate PDF highlight.
4. Dragging a node/palette element across pages dispatches exactly one
   existing authorized command; invalid drop, stale region or changed
   context must refuse without changing document or History. Keyboard
   alternatives remain accessible.
5. Edits, Undo/Redo, switch/Discard and Save leave no stale image overlays;
   a newer revision cancels older preview/worker work. An ambiguous Save
   remains blocked by the existing Exit Guard and never becomes success
   through preview.
6. Failure tests: revoked nonce/capability, oversized body/PDF, malformed
   geometry, cross-origin URL/worker, disabled PDF.js/CSP, module MIME error,
   failed worker/raster and stale HTTP replies. Present a clear error state
   while preserving the unsaved document state.
7. Responsive sheets and browser zoom: semantic rectangles remain aligned
   at desktop/tablet/mobile widths; Tab/focus/selection and reduced-motion
   preserve accessibility. No 0px width, clipping or horizontal UI leakage.
8. Performance on representative shared PHP hosting: bound response and
   CPU, avoid PDF renders on every keystroke (client coalesces changes),
   retain no more than three rendered canvases per document and enforce the
   8-megapixel per-page canvas limit. Check 100+ pages as a bounded stress
   scenario but never promise full 500-page interactive performance without
   actual timing/memory measurements.
