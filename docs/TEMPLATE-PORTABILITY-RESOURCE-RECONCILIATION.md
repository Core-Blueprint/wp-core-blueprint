# Template Library — FRG-T4-01B Resource Portability Reconciliation

**Date:** 2026-11-05
**Status:** SOURCE audit and proposed Base/consumer boundary — **not** package implementation or FRG-04 contract freeze.
**Baseline:** Base `6f82a7f4a2eba30f9257785aa94cdc85cbce0214`, after FRG-T4-01A merge.
**Scope:** six approved Designer consumers: Contracts, Reports, Automations, Evaluator, Certificates, Invoice & Quotes.

## Decision basis

FRG-T4-01A establishes the canonical asset-free single-template record inside `core-blueprint-data-exchange` JSON v1. It requires `resources: []`. Data Exchange owns the existing bounded envelope, preview/fingerprint/apply lifecycle. Consumer implementations own document grammar, permission checks, safe export selection, asset classification and persistence. No second import engine, global media repository or implicit WordPress attachment-ID portability is permitted. Existing consumer-specific export formats are **not** additional Base formats or a reason to introduce legacy adapters.

Offline portability promises a **complete** template on another compatible site. A copied record containing a source site's attachment ID, missing font, reusable child document, credential, arbitrary URL or private preview path does not fulfil that promise. Import must not silently discard required content, substitute another user's media or activate domain actions.

## Canonical resource classes

1. **Self-contained portable document data:** validated text, structure, semantic tokens, safe layout and stable domain-internal IDs; encoded inside the existing one-template JSON record.
2. **Destination-bound references:** WordPress media/post/user IDs, site-specific URLs, reusable child documents, BrandPreset IDs, foreign provider bindings, access principals, dynamic source authorizations, renderer-specific fonts. Each requires a documented consumer-owned rebind/resolve/deny rule. No auto-lookup based on untrusted titles or slugs.
3. **Required portable binary assets:** image, logo, artwork and similar immutable bytes that are essential to faithful restore; currently demonstrated in Reports and Certificates. Source IDs and preview URLs are never sufficient. A narrowly scoped governed package is justified for this class.
4. **Non-portable/private/runtime material:** credentials, tokens, uploaded proof/issued PDFs, signatures, signing sessions, run logs, personal/customer data, preview URLs, temp filesystem paths, unlicensed assets and executable code. Never bundle by default; refuse export when safe separation is impossible.

## Recommended transport direction (candidate, not executable contract)

**Keep FRG-T4-01A JSON untouched for asset-free templates.** For resource-bearing templates, add only an optional bounded **offline package transport** around the same Data Exchange JSON document and a manifest of exact content-addressed resources. A package is *not* a new import engine, an alternate domain schema or an online service. Do not generalize ZIP support until a concrete Reports and Certificates fixture demonstrates the need.

Before any package API or format freeze, define and test these minimum invariants:

- **Identity:** package declares Base format/version and the exact canonical provider/entity/Designer schema; every embedded resource has a stable package-local key, declared media type, original byte size and SHA-256. Never rely on source filesystem paths, WordPress IDs or user-entered filenames for destination authority.
- **Integrity and consistency:** bounded archive parsing rejects path traversal, symlinks, duplicate/case-colliding paths, encrypted entries, extra members, decompression bombs, unsupported compression and excessive resource totals. Verify every byte against the declared digest; bind the manifest, digest set, consumer's selected destination/rebindings and canonical JSON content to the **same import preflight decision/fingerprint**. Recheck digests, permissions and current destination state before writing. A digest is integrity evidence, **not a signature or origin trust**.
- **Consumer authority:** the owning extension alone determines whether a resource may be exported, imported and stored. It performs MIME/content checks and SVG sanitization or refusal, storage quota and license/rights checks, malware/security checks where appropriate, mapping to new local asset IDs, domain document revalidation and draft-only persistence. A package file cannot grant rights.
- **Failure and recovery:** preview writes nothing. On apply, stage validated resources privately and track which consumer-owned resources were created; after a failure provide explicit cleanup/retry and a truthful partial/failed result. Do not promise cross-DB/filesystem transactions or silently leave an enabled/partially restored template.
- **Portability:** users must be able to export a complete file, import offline on a fresh compatible site, review changed associations and verify identical approved visible content. No automatic downloads or vendor account. File rights, authorizations and site-local IDs never move with it.

Do **not** place raw binary bytes into Data Exchange import plan payloads or inflate the existing 10 MiB JSON transport bound. An eventual package adapter may validate the package and supply an authorized, bounded **resource digest/rebinding projection** to a consumer EntityInterface through explicit import context, while Data Exchange remains the only preview/apply orchestrator. Its implementation/API and data binding require a separate SOURCE design and tests; existing generic `array $context` alone is not proof of safe end-to-end storage.

## FRG-T4-01B exit gates and sequencing

**Already evidenced:** six consumer source inventories, exact Base Data Exchange v1 boundary, two real media-bearing domains (Reports and Certificates), no binary requirement proven for other current schemas.

**Must settle before FRG-04 Foundation Freeze:** compact package envelope/manifest and validation ownership, integrity/fingerprint binding design, asset limits/allowed types, cross-site dependency/rebinding contract, rejection/recovery rules and a test-provider fixture for resource-bearing package plan binding. The actual archive verifier and consumer media ingest still require independent runtime evidence. If any of these remain undecided, hold that resource-package contract as an explicit separate gate; do not claim full offline restore for media-bearing templates.

**Consumer modernization remains HOLD** until Base Foundation Freeze. Later consumers implement their own providers/endpoints and execute true site-A-to-site-B artifact round trips: Contracts external reference rebinding; Reports logo; Automations disabled workflow; Evaluator draft and safe links; Certificates image/artwork; Invoice & Quotes template-only copy. Respect the no-legacy/no-historical-test-data-migration policy.

**Senior decision:** do not build a global ZIP engine now. Resolve only the minimum resource-package boundary using a real Reports and Certificates test fixture, then implement one governed adapter if contract evidence proves it necessary.
