# Core Blueprint Base release process

Base retains the canonical `core-blueprint/` directory and
`core-blueprint/core-blueprint.php` basename. The stable launch version is
`1.0.0` in both the plugin header and `CB_CORE_VERSION`.

## Canonical build

Prepare the isolated test environment documented in `tests/README.md`, install
locked development dependencies, and refresh its canonical plugin copy from the
candidate. Then run:

```bash
python3 tools/build-release
```

This command now owns required tool/dependency preflight, PHP syntax/localization,
JavaScript syntax/regressions, WordPress integration, source/test-copy parity,
archive integrity and package verification. It refuses to publish a new release
ZIP or checksum when any required gate fails. See `tools/README.md` for the exact
requirements and gate order. No alternate builder or skip-gates path exists.

Output is `dist/core-blueprint-1.0.0.zip` and its `.sha256` sidecar. A GitHub
source ZIP is not an installable customer release archive. The source/runtime
inputs are read-only during packaging.

## Installation, field proof and approval

Run `tests/bin/run-release-install-scenario.sh` against the exact candidate ZIP,
a deliberately selected previous ZIP, checksum-verified WP-CLI and an isolated
test database. This checks fresh activation and same-version replacement.

Media Replace HTTP-upload field checks, source SHA, artifact hash and final
review remain explicit release evidence. See
`docs/base-launch-closure-2026-09-16.md` for the current candidate's evidence and
remaining holds. A successful build alone does not authorize merge or release.

## Publisher-signed Designer artifact (P0-PRODUCT-01)

The canonical manifest is accompanied by a detached `artifact-manifest.sig`,
signed with Ed25519 over
`CoreBlueprint/Base/ArtifactManifest/Ed25519/v1\0 || SHA256(raw manifest bytes)`.
The signer uses a 64-byte libsodium secret key supplied only by the authorized
offline release environment through `CB_CORE_ARTIFACT_SIGNING_KEY_FILE`.
The file must be outside the checkout with private permissions and is never
packaged, printed, generated by the builder or committed. Both build entrypoints
refuse unsigned Designer artifacts.

The runtime pins the independently approved publisher verification key in
`PublisherSignature::TRUSTED_PUBLIC_KEY_BASE64`, validates the detached
signature and then performs the existing complete InstalledVerifier and
module/CSS verification. The old wp-config checksum constant is no longer
required or consulted. Signatures are checked automatically on use after a
fresh installation or update; there is no installation-time trust on first use,
local approval record or dependency on a verification server.

**Release blocker:** neither a production publisher signing identity nor its
independently authenticated bootstrap/distribution channel has been approved.
The pinned key is intentionally empty and all unsigned/untrusted artifacts fail
closed. A public key shipped solely within an untrusted ZIP is not an
independent trust anchor: an attacker who replaces all executable PHP can also
replace the verifier. Independently establish and publish the publisher key
fingerprint and authenticated official installation/update provenance before
claiming that arbitrary uploaded ZIPs are cryptographically authenticated.
No official customer release or clean-install acceptance can pass until that
separate owner decision and signing are complete.
