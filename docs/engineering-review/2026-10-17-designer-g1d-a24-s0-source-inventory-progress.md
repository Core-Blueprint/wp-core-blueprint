## 2. Hook/cache and single-site boundaries

- The Base Settings writer currently uses WordPress `update_option`, with WordPress pre-update filters, update hooks, autoload and object-cache semantics. A raw SQL CAS is **not** a drop-in replacement without a proven compatibility policy. Audit registration of `pre_update_option_cb_core_settings`, `pre_update_option`, `update_option_cb_core_settings`, `update_option`, `updated_option`, `pre_option_cb_core_settings`, `option_cb_core_settings` and dynamic callback registration across the *whole tracked checkout*. Absence in a partial scan is not an absence claim.
- Relevant caches: `Settings::$cached`, `wp_cache` options group (per-option key, `alloptions`, `notoptions`), optional persistent object cache, and autoload policy. Reject cache-after-commit mismatch; WordPress runtime acceptance later is mandatory.
- **Multisite is currently unsupported by Base v1.** Inventory shared WP APIs and guards, but do not advertise or accidentally introduce multisite support during A2.4.
- Third-party plugins can register dynamic Options hooks at runtime; source-only first-party evidence cannot establish installed-hook compatibility. Such hooks require a later authorized WordPress Level 2/field inspection.
